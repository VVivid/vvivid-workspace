## Resource decisions

The only new config property is the optional `shopping_origin`, proposed value `https://shopping.vvivid.dev`. It requires a canonical HTTPS origin with no path/query/fragment/trailing slash, an HTTPS issuer, and a hostname distinct from the configured SSH resource and issuer. No arbitrary client map or dynamic registration is added.

| Client | Permitted resource |
| --- | --- |
| sshmcp-codex / sshmcp-chatgpt | Existing `resource` value, unchanged |
| shopping-web | `shopping_origin` + `/api/v1` |
| shopping-codex / shopping-chatgpt | `shopping_origin` + `/mcp` |

Mapped clients must supply exactly one matching resource for authorization GET/POST and authorization-code exchange. A refresh may omit resource, preserving the original grant audience; an explicit target must match the same client binding. An empty target is not omission. With no `shopping_origin`, all three shopping IDs fail closed, including refresh.

Other realm clients retain the baseline behavior: omitted resource or the existing SSH target can reach Keycloak, which still validates client registration, credentials and grants. They cannot select either shopping resource. This preserves account-console/other realm flows without creating a global five-client allowlist. Do not claim the guard rejects every unregistered client; it prevents shopping target selection by those clients.

The issuer, public Host, trusted forwarded origin, fixed loopback upstream, canonical routes, concurrency/body/time bounds and existing SSH rules remain. Duplicate resource/client/grant parameters, token parameters in query, Basic/body client disagreement and noncanonical paths fail before upstream. Basic client identity is form-decoded once, matching Keycloak 26.8.1, while the original Authorization header and secret are forwarded unchanged. Malformed Basic encodings and repeated Authorization headers are rejected to prevent differing parser decisions.

Keycloak 26.8.1's tagged [`BasicAuthHelper.RFC6749.parseHeader`](https://github.com/keycloak/keycloak/blob/26.8.1/core/src/main/java/org/keycloak/util/BasicAuthHelper.java) decodes the Basic username; [`ClientIdAndSecretAuthenticator.authenticateClient`](https://github.com/keycloak/keycloak/blob/26.8.1/services/src/main/java/org/keycloak/authentication/authenticators/client/ClientIdAndSecretAuthenticator.java) uses that helper. This is why classifying Go's raw Basic username would let an encoded shopping ID fall into the legacy path. The guard normalizes only its local comparison and never rewrites credentials.

Keycloak owns client authentication, grant ownership, PKCE, consent, allowed grants, signing and audience/scope issuance. The proxy neither changes grant types nor adds scopes/audiences. Configuring canonical resource IDs/audience mappers, shopping-only scope assignments and disabled unrelated grants is still a required live prerequisite. Local fake-peer tests establish routing/denial and request preservation, not actual Keycloak token issuance or client interoperability.
