# GitHub live deployment

The [website workflow](../../../.github/workflows/website.yml) builds the complete
Linux amd64 Hugo/nginx image, checks its HTTP responses and guide exclusion, and
publishes `ghcr.io/vvivid/vvivid-website:sha-<commit>` with `GITHUB_TOKEN`.
Deployment uses the registry's immutable `sha256` digest, not the tag. Pushes to
`main` trigger this only for `vvivid.dev/**` or the website workflow itself.
Pull requests run checks with `contents: read` and receive no publishing,
Tailscale, SSH, or deployment permissions. Native website Make targets still
render locally without Docker or deployment credentials.

The live job joins Tailscale with a short-lived GitHub OIDC identity and sends
one command to a restricted SSH account. The root-owned helper fixes the image
repository, Compose project `private-edge`, existing infrastructure path, and
service `vvivid-live`. It never starts dependencies. The existing
`vvivid-preview` service, its image expression, shared `VVIVID_IMAGE`, and its
GitLab preview pipeline stay unchanged by a live deployment. The separate
[preview workflow and runbook](../preview/README.md) own migration of preview
from `release/vvivid-preview`.

Search-related host routing and preview noindex activation are separate from this
live-image update. See the [search operations runbook](../seo/README.md); deploying
this live image alone cannot update the existing preview's responses.

These files prepare the deployment. They do not install access, alter the server,
or establish that this workflow has deployed successfully. Source publication,
one-time setup, and live activation require their corresponding authorization.

## One-time setup

Use this order during the approved activation. Keep private hostnames, addresses,
ports, keys, and local health endpoints in runtime configuration. Do not place
them in the repository or ask anyone to paste private keys into chat.

### GitHub environment and package

Create the `vvivid-live` environment in `VVivid/vvivid-workspace`. Under deployment
branches, select only `main`; do not allow tags. Hold the first deployment with a
required reviewer until the image is published, its package is public, and server
setup is verified. Choose the continuing review rule deliberately: removing that
initial reviewer allows subsequent relevant `main` updates to deploy
automatically. Branch rules and workflow review protect code that can publish
images or use the deployment identity.

Configure these values on the **environment**, rather than for pull requests:

| Kind | Name | Value |
| --- | --- | --- |
| Variable | `TS_CLIENT_ID` | Tailscale federated identity client ID |
| Variable | `TS_AUDIENCE` | Exact audience generated by Tailscale |
| Variable | `VVIVID_DEPLOY_HOST` | Server MagicDNS hostname or Tailscale address |
| Variable | `VVIVID_DEPLOY_PORT` | Existing server SSH port |
| Secret | `VVIVID_DEPLOY_SSH_KEY` | Dedicated Ed25519 private key, without a passphrase |
| Secret | `VVIVID_DEPLOY_KNOWN_HOSTS` | Verified SSH host-key line for `[hostname]:port` |

Verify the server host-key fingerprint through the existing trusted admin
connection before saving the known-hosts line. The workflow enables strict host
verification; it does not learn host keys from `ssh-keyscan` at deployment time.
Create the dedicated key on a trusted administrator machine and install only its
public half on the server. Protect or delete the local private copy according to
the administrator's credential policy after storing the environment secret.

The build job needs repository Actions access to create/write its linked GHCR
package. Its source label links the image to this repository. After the first
successful publish, open the `vvivid-website` package settings under the `VVivid`
account and change its visibility to **Public**. A public source repository does
not make the package public automatically. Confirm an unauthenticated pull of
the exact published digest from the server before releasing the initial
environment approval. The helper pulls before changing live, so a private or
missing package fails safely. No server registry-write token is needed.

### Tailscale federation and policy

In Tailscale **Settings → Trust credentials → Credential → OpenID Connect**,
create a dedicated credential with these exact constraints:

| Field | Value |
| --- | --- |
| Issuer | GitHub / `https://token.actions.githubusercontent.com` |
| Subject | `repo:VVivid/vvivid-workspace:environment:vvivid-live` |
| Custom claim `repository` | `VVivid/vvivid-workspace` |
| Custom claim `ref` | `refs/heads/main` |
| Custom claim `workflow_ref` | `VVivid/vvivid-workspace/.github/workflows/website.yml@refs/heads/main` |
| Scope | Writable `auth_keys` only |
| Tag | `tag:vvivid-live-ci` |

The environment changes GitHub's `sub` claim: use the environment subject above,
not a `ref:refs/heads/main` subject. The additional claims constrain the branch
and workflow. Save Tailscale's generated client ID and audience in the GitHub
environment variables above. The audience has the form
`api.tailscale.com/<client-ID>`. These two values are not secrets; no reusable
Tailscale OAuth secret or auth key is used.

Merge a narrow policy grant into the existing tailnet policy. Define a host alias
for this server using its actual Tailscale address in the private policy, and let
`tag:vvivid-live-ci` reach only that host's existing TCP SSH port. For example,
replace the placeholders below in the Tailscale admin console:

```jsonc
{
  "tagOwners": {"tag:vvivid-live-ci": ["autogroup:admin"]},
  "hosts": {"vvivid-live-server": "<server-tailnet-address>"},
  "grants": [{
    "src": ["tag:vvivid-live-ci"],
    "dst": ["vvivid-live-server"],
    "ip": ["tcp:<existing-ssh-port>"]
  }]
}
```

Tailscale grants are additive: inspect existing broad grants/ACLs so this tag does
not inherit access to other services. Preserve existing administrator and preview
access; the server can remain untagged. This uses ordinary OpenSSH over
Tailscale, so no Tailscale SSH policy or server SSH-mode change is needed. The
action creates an ephemeral node and removes it when the job finishes. The
pinned v4 action supports OIDC and installs a supported Tailscale release.

Official references: [workload identity federation](https://tailscale.com/kb/1581/workload-identity-federation),
[pinned GitHub action](https://github.com/tailscale/github-action/blob/99a8333667fff04fdd6cffb46dfd409f8329a7bf/README.md),
and [GitHub OIDC claims](https://docs.github.com/en/actions/reference/security/oidc).

### Restricted server identity

The approved server setup needs Python 3, Docker with Compose, curl, OpenSSH,
sudo, and a local filesystem supporting `flock`. The helper's fixed Compose path
is `/home/admin/infrastructure/compose.yml`, with the existing sibling `.env`;
review and deliberately update the source constants if the infrastructure moves.

Create a system account `vvivid-deploy`, with a locked password, shell `/bin/sh`,
no writable login home, and no `docker`, `sudo`, or administrator group
memberships. Do not use `/usr/sbin/nologin`: OpenSSH must be able to execute its
forced command. The account creation command is:

```sh
sudo useradd --system --user-group --no-create-home --home-dir /nonexistent --shell /bin/sh vvivid-deploy
sudo passwd --lock vvivid-deploy
```

Install the reviewed files as root, from this directory in a trusted checkout:

```sh
sudo install -d -o root -g root -m 755 /usr/local/libexec /etc/vvivid-live
sudo install -o root -g root -m 755 deploy.py /usr/local/sbin/vvivid-live-deploy
sudo install -o root -g root -m 755 ssh-entrypoint.py /usr/local/libexec/vvivid-live-ssh
sudo install -d -o root -g root -m 755 /etc/ssh/authorized_keys
```

Create `/etc/ssh/authorized_keys/vvivid-deploy`, root-owned mode `0644`, containing
only the dedicated public key prefixed by:

```text
restrict,command="/usr/local/libexec/vvivid-live-ssh" ssh-ed25519 <dedicated-public-key> vvivid-live-github
```

The public key must be readable when OpenSSH opens it as the deployment user;
the root-owned file and directory prevent that user from changing it.

Install [sshd-vvivid-live.conf.example](sshd-vvivid-live.conf.example) as
`/etc/ssh/sshd_config.d/90-vvivid-live.conf` only if the server's main SSH config
includes that directory. It fixes the authorized-key location and forced command,
rejects password login, PTYs, forwarding, and user startup scripts. Keep the
existing listener/port and admin connection. Run `sudo sshd -t`, then inspect the
effective `sshd -T -C user=vvivid-deploy,host=localhost,addr=<runner-tailnet-address>`
configuration before reloading SSH. Verify existing administrator access still
works before closing the trusted session.

Validate [sudoers-vvivid-live.example](sudoers-vvivid-live.example) with
`sudo visudo -cf <staged-file>` and install it as
`/etc/sudoers.d/vvivid-live`, root-owned mode `0440`. The sole allowed root program
validates exactly one lowercase digest before running any commands. The SSH
entrypoint accepts only `deploy sha256:<64 lowercase hex digits>` and uses argv
execution, never shell evaluation. Root code is installed during setup; a deploy
never uploads or runs code supplied by the runner.

Create `/etc/vvivid-live/health-url`, root-owned mode `0600`, containing the actual
server-local Traefik HTTP origin, such as `http://<server-tailnet-address>/`.
Use the existing Traefik bind address, not an assumed loopback listener. The
helper sends `Host: vvivid.dev` and also checks public `https://vvivid.dev/`.

The helper is shared with preview; its root-owned installed basename fixes its
scope. Keep this exact live installation name. Both updated helpers lock
`/run/lock/vvivid-deployment.lock` for their entire transaction because `.env` is
shared. Before enabling preview, hold both deployment environments, drain all
active/queued deployments, and update this installed live helper first. Old live
versions use a different lock and cannot safely overlap preview. Follow the
[shared-lock migration](../preview/README.md#server-installation-and-shared-lock-migration).

### Existing Compose configuration and cutover

Record the current live container image/image ID and the current live settings
before changing configuration. Preserve the existing Compose project name
`private-edge`; a different project can create competing containers and routers.
Edit only the existing `vvivid-live.image` line to the expression in
[compose-live-image.example.yml](compose-live-image.example.yml):

```yaml
image: ${VVIVID_LIVE_IMAGE:-${VVIVID_IMAGE}:${VVIVID_LIVE_TAG}}
```

Keep every existing live option, label, network, and container name. Keep the
preview image expression and global `VVIVID_IMAGE` intact. Leave
`VVIVID_LIVE_IMAGE` absent initially: the nested fallback preserves the current
legacy image. Validate normalized `docker compose --project-name private-edge
--env-file /home/admin/infrastructure/.env --file
/home/admin/infrastructure/compose.yml config --format json` before and after.
With no new key the entire configuration must match. With a temporary
`VVIVID_LIVE_IMAGE=ghcr.io/vvivid/vvivid-website@sha256:<digest>` environment
override, only `services.vvivid-live.image` may differ. Configuration validation
does not recreate a service.

At cutover, disable **only the old GitLab live deployment job/tag trigger** in the
old website project. Prevent it from racing with GitHub or persisting an obsolete
live tag. Leave the old preview build/deploy and its shared settings available.
Do not change the archived GitLab reference here to manage that external job.
For the archived pipeline's structure, the exact source change in that external
project is to replace only `deploy_live.rules` with:

```yaml
deploy_live:
  # Keep the rest of this job unchanged for historical reference.
  rules:
    - when: never
```

Use a commit message containing `[skip ci]` for this configuration-only cutover
change so it does not start a preview pipeline. Publication to the old repository
requires explicit permission covering that ref. Cancel only any already queued
or running **live** jobs and do not rerun historical tag pipelines with their old
live configuration. Do not disable the whole old project, edit preview rules,
or restart the GitLab runner.

The old runner has a file bind of the shared infrastructure `.env`. The helper's
atomic replacement changes its inode, so that existing bind continues seeing the
old file. Preview values are unchanged at cutover, so leave the runner running;
future changes to shared preview settings need coordination with that mount.
Confirm the package pull, restricted SSH rejection cases, environment branch
restriction, and local/public baseline health, then release the first live job.

The activation acceptance evidence is the exact live image digest and image ID,
local Traefik HTTP 200 for `Host: vvivid.dev`, public HTTPS 200, and unchanged
preview image/container state. Keep the former live image available for rollback;
do not run legacy cleanup scripts or registry cleanup during cutover.

## Deployment and recovery

GitHub serializes live jobs with `cancel-in-progress: false`; a server `flock`
also serializes live and preview helper invocations through the shared
`/run/lock/vvivid-deployment.lock`. A waiting run is skipped if the
website tree or deployment workflow has changed on `main`. An unrelated monorepo
commit does not discard a valid website deployment. GitHub may replace an older
pending job with a newer one; an already running deployment is not cancelled by
this concurrency setting.

The helper refuses an out-of-sync Compose/running baseline, then pulls the exact
candidate before writing `.env`. It atomically replaces only
`VVIVID_LIVE_IMAGE`, preserving the shared file's ownership, permissions, and
unrelated settings. It uses `compose up --detach --no-deps --pull never
vvivid-live`. Before either HTTP check can pass it verifies the running
container's configured image **and actual Docker image ID** against the candidate.
This prevents a cached public HTTP 200 from masking a failed container update.

Recreation failures, health failures, and handled interruption signals restore
the previous key state and recreate only live with the previous image. Restoration
preserves unrelated `.env` updates made while checks were running. Rollback must
also pass container/local/public checks; the workflow fails even after a
successful rollback. `ROLLBACK FAILED` requires administrator intervention.
An abrupt host failure or uncatchable kill can interrupt recovery; inspect the
live image, persisted key, and health before retrying. Do not bypass a baseline
mismatch blindly or restore an old whole `.env` over newer preview settings.

For an intentional redeploy/rollback, open the website workflow's **Run workflow**
on branch `main` and provide a previously published lowercase `sha256:<digest>`
in `image_digest`. The same repository restriction, environment, lock, and health
checks apply. Leaving the input empty rebuilds and deploys current `main`.
Manual deployment cannot select another registry or change preview. The first
deployment can automatically restore the legacy image on failure; selecting a
legacy registry image manually requires a separately authorized administrator
change rather than widening the restricted helper.

To withdraw this access, block the GitHub environment first, revoke the dedicated
Tailscale federated credential, and remove the dedicated SSH key/sudo rule and
account configuration with administrator access. This does not itself roll back
the running site. A full cutover reversal must deliberately restore the prior
live image/setting and only its Compose expression before considering the old
live job; preview configuration remains outside this procedure.

## Local checks

```sh
make -C vvivid.dev deployment-test
HUGO=/absolute/path/to/pinned/hugo make website-check website-test website-build
docker build --platform linux/amd64 --tag vvivid-website:check ./vvivid.dev
./vvivid.dev/scripts/smoke-image.sh vvivid-website:check
```

The Python standard-library tests replace all Docker/HTTP commands. They cover
ordering, registry denial, partial recreation, local/public health failures,
incorrect running images despite HTTP 200, interruption, previous-state recovery,
both fixed scopes, other-service setting preservation, SSH command rejection,
exact branch routing/build URLs, stale-run gates, and actual interprocess lock
serialization across live and preview updates/rollback. The smoke check runs only a temporary local container,
validates nginx and HTTP, checks guide files are absent, and checks case variants
and nested guide URLs return 404. It removes its temporary container on exit.
