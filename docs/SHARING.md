## Owner flow

My list → Share enters selection mode. Its checkboxes select items for disclosure and do not change picked-up state. Cancel leaves the original list intact; Select all/Deselect all and the selected-count Create link button remain compact. Creating a link opens a modal containing only its URL and Copy link button. Escape or tapping its backdrop dismisses it; native dialog focus handling restores Share. Screen-reader status announces successful copying or the select-to-copy fallback.

`POST /api/v1/lists/{list_id}/shares` requires a genuine browser session, `shopping:read`, `shopping:lists:write`, exact Origin/CSRF, an idempotency key, the current list revision and 1–500 distinct selected items with current item and product revisions. A missing, foreign, removed or stale selection fails atomically. Product revision pins prevent a catalog edit from silently changing the facts selected for disclosure. Creating at most 20 links per owner per rolling hour bounds capability creation. An exact creation retry returns its original code and deadline, even if the list/catalog has since changed; it never creates another link or restarts the clock. Disabled owners cannot create or replay shares.

The browser settles creation only after receiving a result whose code is exactly five ASCII letters and recovering its URL. Interrupted, unparseable, null, missing or malformed successful results leave creation unresolved; Retry replays the original endpoint, key, body and selection revisions. A first definitive rejection settles that attempt. Once any creation attempt has an unknown outcome, a later rejected retry cannot disprove an earlier commit and must preserve the operation. In-page private-list Refresh may update CSRF and current list content, but it has no share URL and cannot settle unresolved creation. Retry stays available and competing controls stay locked until valid replay recovers the same URL. Starting Retry aborts an older refresh before it can install stale content. This does not change ordinary list-edit refresh settlement or the server's disabled-owner/expiry checks.

## Public copy

A link has exactly five uniformly sampled ASCII letters from `a–z` and `A–Z`, with case-sensitive matching: 52^5 possible codes. Codes use `crypto/rand`. SQLite uniquely reserves their SHA-256 hashes, retries collisions at most 16 times and keeps expired reservations. There is no deletion or code-recycling path. An old link therefore cannot reveal a later share. Raw codes are present in the owner's durable creation result to support exact replay; codes and write capabilities are excluded from activity summaries and application request logs.

`GET /s/{code}` needs no account or sign-in and never resolves a browser session. It shows the Shopping brand, “A little shopping help”, retailer context, category icons, selected names, pack facts, requested quantities, pickup checkboxes and time left. It contains no owner identity, personal list/product IDs, unselected products, description/media/source URLs, purchase records or prices. Snapshot facts survive catalog/list edits and restarts. Picked-up state starts unchecked and belongs to the public copy; guest actions cannot change the owner's list, purchases or Insights.

`PATCH /s/{code}/items/{position}` sets an explicit boolean at an expected guest-item revision. It requires exact same-origin Origin, a custom header containing the separate 128-bit random write capability issued with that page, bounded JSON and an idempotency key. No browser/session cookie authorizes these writes. No CORS permission is issued. Guest data, the original replay result and an explicitly anonymous immutable guest audit event commit together. Different payloads under one key and concurrent stale edits conflict. Rejected attempts reserve no key; an unknown network outcome keeps the exact endpoint/key/body for Retry. A rejected retry followed by any failed refresh also retains that operation and its Retry action, with stale checkboxes locked. Only a successful write response or authoritative successful refresh settles the pending operation; expiry/404 still removes the items and capability.

## Lifetime and abuse bounds

A schema check fixes expiration to creation + 21,600,000 milliseconds. Every public read and write, including a cached write replay, checks the deadline and the owner's enabled state on the server. Expiry returns the same generic unavailable page as invalid links, with no item data. Writes also recheck time before commit. Guest edits and owner retries cannot extend the deadline. The guest script removes items and its write capability from an already-open page when its countdown expires and revalidates on focus/visibility and every 30 seconds. The server remains authoritative. JavaScript is required for live checkboxes/countdown; without it the page advises reloading to check availability.

The entire public `/s` surface has one fixed-size in-process request bucket: burst 60, refill one request per two seconds (30/minute), including invalid paths, valid reads, writes and retries. Throttled requests return 429/Retry-After. This bounds distributed guessing to at most 10,860 attempts per uninterrupted six-hour window before accounting for legitimate traffic. It uses no request-supplied forwarding/IP headers or unbounded client maps and works when Traefik is the sole peer. This personal-app tradeoff lets heavy public traffic temporarily affect other guest links; private shopping/auth/health routes have a separate path and remain available. A process restart resets this transient request allowance. The checklist and exact mutation outcomes remain durable. No proxy configuration change is required.

Public responses use no-store, no-referrer, noindex/nofollow/noarchive, the existing strict CSP and no third-party scripts or product images. Application logs contain route patterns and fresh correlation IDs. Existing proxy/browser URL histories are outside this local implementation's log validation.

Expired snapshots and anonymous events remain in SQLite with the permanent code reservations; expiry removes public access, not database records. No cleanup job, revocation UI, household sharing, MCP sharing tool, dependency, infrastructure setting or autonomous network work is added. All migrations and transactions follow the existing server-only/no-backup policy.
